UMA Conflict Report

In one in five Polymarket disputes, at least one UMA voter held a position in the market they were deciding. For markets over $1M, it was two in three. Nothing in the protocol filters them out.

What this does and does not show. 47% of conflicted votes went to the side the voter held. But the detectable conflicted stake is small: 0.004% of all vote weight, at most 1.32% in any single dispute. Removing every conflicted voter changes 0 outcomes and pushes 0 below the 65% supermajority. The finding is not that outcomes were flipped. It is that conflicted jurors routinely sit on cases, and nothing filters them.

Method

  1. Votes. Resolved YES_OR_NO_QUERY price requests and their revealed votes (voter, price, tokens) from the final, deciding round, via UMA's public mainnet-voting-v2 subgraph.
  2. Question text. Ancillary data recovered from OracleChildTunnel logs on Polygon and matched by keccak hash.
  3. Market match. Polymarket questionID = keccak(ancillary data before ",ooRequester:"), looked up on the Gamma API. Accepted only on an exact questionID match or an exact title match (mostly negRisk markets). 4,213 of 4,549 requests mapped.
  4. Voter → wallet. Each voter's Polymarket Safe address is derived deterministically with CREATE2 from the voter address (Polymarket Safe factory). The derivation was verified on a sample by calling getOwners() on-chain: the Safe's owner is the voting address. A Safe at that address can only be controlled by the key that cast the vote, unless its owners were later changed. Funding-graph heuristics were not used.
  5. Position at vote time. Polymarket Data API activity (trade, split, merge, redeem) in that market up to the round's last reveal time. A voter is "conflicted" if they held a net ≥ 1 share of any outcome.
  6. Counterfactual. Vote weight per answer recomputed without conflicted voters; checked for a different winner, the 65% supermajority (SPAT) and the participation threshold (GAT).

Download the data

Everything on this page is regenerated daily from public sources and published as an open dataset under CC BY 4.0. Column definitions, method and citation: data README.

  • summary.json: headline numbers (the figures above).
  • disputes.csv: one row per DVM request mapped to a Polymarket market (4,213 rows).
  • conflicts.csv: one row per vote cast by a voter holding a position in that market (2,256 rows).

Reproduce it: pip install requests pycryptodome && python conflict-report/conflict_report.py --incremental (source).

Limitations

  • This is a lower bound. Only the Safe derived from the voting address (and the address itself) is checked. Voters trading from separate wallets, exchanges, email/magic-link accounts or newer deposit wallets are invisible here. Large holders are the most likely to split wallets, so the 0.004% weight figure is almost certainly an undercount.
  • Transfers of outcome tokens between wallets and negRisk conversions are not reconstructed.
  • The Data API caps pagination at about 10,000 events per market chunk; extremely active traders may be truncated.
  • Gamma volume is zero or missing for some markets. 336 requests could not be mapped to a market.
  • Voting one's own side is not proof of bad faith. Most conflicted voters also voted with the correct majority.
  • Some markets have two DVM requests (re-votes), so a voter can appear twice for one market.

How Saring fixes this

Saring is a conflict-blind jury for prediction-market disputes, built on Solana with Arcium multi-party computation. The conflict check happens inside MPC, so the filter never becomes a public list.

  1. Silent exclusion. Inside Arcium MPC, each juror's ballot is checked against positions in the disputed market. Jurors holding a position are excluded from the tally.
  2. The chain never sees the jury. Juror ids, trader ids and ballots go on chain only as ciphertexts, and the MPC never reveals which jurors were excluded. (In the current MVP the court authority seats the jurors and relays the positions, so it knows both lists.)
  3. Bribe receipts are worthless. Each seat has a secret ballot key held inside MPC. A ballot counts only with the seat's current key, and a ballot can rotate the key, so a key handed to a briber after rotation is worthless and the briber can't tell. Forged ballots with guessed keys are ignored inside MPC.
  4. Minimal output. The only thing revealed is (yes, no, excluded, incomplete).
